Segment Pacing Board

One consistent pacing view for every client — a single row for small accounts, one row per allocated segment for large ones. Same columns, same daily heat calendar; only the number of rows flexes.

TabPacing (existing)
Branchfeature/ads-api

DateSeptember 2026

1The idea

Take each client's budget, break it into however many segments that client actually works at, and show — for each — how spend is pacing against a daily target.

The reference is a spreadsheet "pacing board": every row is a budget segment, and across it you see the segment's monthly budget, its daily-average budget, trailing-window spend (month-to-date, yesterday, last 3 days, last 7 days) each measured against pace, a rest-of-month suggestion, and a day-by-day heat calendar of spend. We are rebuilding that inside the app's Pacing tab, driven by live data instead of a manual sheet.

The one principle

The view never changes — only the number of rows does. A small client whose budget is too small to split shows one row (the whole account). A large client whose budget has been allocated across segments shows one row per segment plus a Total. Identical columns, identical math, identical calendar.

3Where the rows come from

The app picks the finest budget breakdown a client actually has — asking four questions in order and stopping at the first "yes."

1
Has the Budget Allocation engine been run? → Use its segments as the rows (e.g. 12 Brand/Region/Category cells → 12 rows). This is what "the breakout is a function of the allocation engine" means.
2
If not — did they upload committed budget lines split into segments? → Use those lines as the rows (e.g. 4 budget lines → 4 rows).
3
If not — is there a single total monthly budget? → One row = the whole account. This is the small-client case.
4
If there's no budget at all? → Still one row, showing spend only (no Diff, since there's nothing to pace against).

Nobody configures this. Each client lands on exactly one branch automatically, and the board renders 1…N rows accordingly. A Total row appears only when there is more than one row. The single-row case is account-level pacing — same code, same layout, one line.

4The pacing math

Everything compares to the daily-average budget, scaled to each window — never a flat monthly average.

QuantityDefinition
Daily-avg budgetMonth budget ÷ days in month
Expected (per window)Daily-avg × N — where N = 1 (Yesterday), 3 (Last-3), 7 (Last-7), or days-elapsed (MTD)
Diff $Actual spend − Expected
Diff %Diff $ ÷ Expected
Rest of month — LeftMonth budget − MTD spend
Rest of month — Suggested/dayLeft ÷ days remaining

Anchored to data, not the wall clock

"Days elapsed", "Yesterday", and the trailing windows are measured from the last day that actually has data, not today's calendar date — matching the app's existing pacing logic. This stops a stale upload from raising a false "under-pacing" alarm. ("Days remaining" = days in month − days elapsed, a small new addition.)

6How it's built

Backend — a new _pacing_grid(), emitted as pacing_grid in the bundle

  1. Anchor the current month; compute days-in-month, data_through (last day with data), days-elapsed, days-remaining.
  2. Resolve the per-segment monthly budget via the four-question fallback in §3.
  3. Build the resolver; read campaign_performance for the month; accumulate spend[segment][day]. Campaigns with no mapping fall into an (unmapped) row so totals always reconcile.
  4. Per row, compute the daily-avg budget, the four windows with Diff $/%, rest-of-month, and the days: [{date, spend}] array for the calendar.
  5. Return rows + a grand totals row.

Frontend — extend the Pacing screen

  1. A single PacingGrid component: the summary columns (Segment · Month Bg · Daily Avg · MTD · Yesterday · Last-3 · Last-7 · Rest-of-Month), with Region/Brand grouping + subtotals and a Total row when rows > 1.
  2. A daily heat calendar beside it: one column per day, each cell colored by spend vs the row's daily target (calm near target, red over, amber under; future days neutral). Horizontally scrollable.
  3. Types added to types.ts; the existing account-level pacing chart folds into the one-row case.

Consistency

One component renders every client. The small-client view is not a special case — it's the same grid with a single row.

Reconciliation

Row spend always sums to the Total; unmapped campaigns are shown, never dropped, so the numbers foot.

7Data dependency & graceful degradation

The board self-adjusts to what a client has — it never breaks.

  • Daily calendar needs daily campaign data. The account-level "pacing" export has no campaign breakdown and can't be segmented. If a client only has monthly campaign data, we show the summary columns at month grain and hide the calendar (with a small note) rather than error.
  • Unmapped campaigns → an (unmapped) row, so totals still reconcile.
  • No budget at all → spend-only row(s), no Diff — never an error.

This mirrors the "self-activating, nothing breaks" approach used for the interactive Map feature.

8Out of scope

Not building (for now)

Sub-Region and Store Count. These appear in the reference spreadsheet but are retail-specific attributes that do not exist anywhere in our data model — no column, table, or ingestion path. Adding them would be a greenfield dimension (new ingestion + resolver support) and is deferred until there is a data source for them. Segmentation uses the budget engine's own dimensions: Brand / Region / Category.

9Open item to confirm

Decision

Per-segment budget source. Default per §3: use the latest Budget Allocation run (rec_spend) as each segment's monthly budget, falling back to committed budget lines, then a single total. Confirm this ordering — or say if larger clients should pace against committed budget lines rather than the allocation engine's recommendation.

Build sequence

  1. Backend _pacing_grid() + bundle field + types.
  2. Frontend PacingGrid summary columns (grouping, subtotals, Total).
  3. Daily heat calendar.
  4. Graceful-degradation states (monthly-only, unmapped, no-budget).
  5. Unit tests (pace math, window anchoring, unmapped bucket, single- vs multi-row) + live verification.
